# ADR-0001：DeepSeek Harness Agent 团队协作与质量门禁插件

- 状态：已接受；无模型专家团面板、角色设置、MissionRun 演示与只读任务账本恢复已实现
- 日期：2026-08-17
- 决策所有者：项目所有者
- 依据：当前对话已确认方案、PlanLens 评审、CC Switch 源码调研

## 结论

开发一个复用 DeepSeek Harness 官方 Subagent、Workflow、ACP 和后台任务能力的本地插件，让 DeepSeek 主会话能够组织多个独立 Agent 完成：

```text
目标 → 规划 → 执行 → 确定性验证 → 独立复审 → 交付
```

插件不是通用的多进程编排平台，也不是单纯的 CLI 安装器。它的职责是把 Agent 选择、角色分配、权限、预算、任务状态、质量关卡、人工干预和审计收敛到一个可控的本地工作流中。

产品价值需要通过对照评测验证，不再只作为未经测量的假设。评测同时回答：外部规划、外部复审以及两者组合分别带来多少质量收益，以及这些收益是否值得额外的延迟、调用次数和维护复杂度。

## 用户问题

DeepSeek 可以执行复杂任务，但用户不希望把规划、执行和最终质量判断全部交给同一个模型。现有本地 Agent 各有优势，却缺少统一的：

- 安装与健康状态可见性。
- 角色和团队配置。
- 跨 Agent 任务交接。
- 确定性验证与独立复审。
- 权限、预算和停止条件。
- 中断恢复、审计和交付边界。

## 产品边界

### 属于本产品

- Agent 面板：发现、版本、路径、冲突、鉴权与 Harness 适配状态。
- 团队方案：协调者、规划者、执行者、验证者、复审者及候补。
- 运行引擎：任务图、预算、超时、质量关卡、人工审批和审计。
- Provider 适配：启动、取消、结果捕获、最小上下文和能力声明。
- Workspace/Artifact/Validator 适配：Git Worktree、独立报告、测试、格式和来源验证。
- 可视化运行面板：Agent 小人、角色徽章、节点状态和轻量状态动效。

### 不属于首条闭环

- Windows、Linux、WSL 的正式支持。
- 多 Agent 并行修改同一工作区及自动合并冲突。
- 自动 Push、PR、发布或部署。
- 云同步、账号系统和遥测。
- 任意第三方 Agent 定义导入。
- 对现有非 Git 目录执行不可逆或无法验证的自动写入。
- 自动重复完成状态不确定的副作用操作。

## 首批 Agent

面板首批展示：

- DeepSeek：Harness 内置协调者和可选执行者。
- Claude Code。
- Codex CLI。
- Antigravity CLI。
- Pi。

“面板可检测”与“正式可参与团队”是两个状态。只有通过启动、取消、超时、权限、结果捕获和恢复能力验证的 Agent 才能标记为正式 Provider；其余 Agent 显示为已检测或实验性，不阻塞整个插件。

## 三层架构

### 1. DeepSeek 主会话

负责理解目标、推荐团队、解释计划和处理用户决策。它可以提出任务图变更，但不能直接扩大权限、预算或绕过强制关卡。

### 2. 确定性插件运行引擎

负责权威任务状态、节点调度、权限策略、预算、超时、审批、持久化、恢复和审计。所有 Agent 调用都必须经过该引擎。

### 3. 独立 Agent 会话

负责规划、执行、研究或复审。Agent 输出自由格式内容和轻量结构化提议，但不能直接写入权威控制状态，也不能私自启动其他 Agent。

## 核心领域对象

| 对象 | 职责 |
|---|---|
| AgentDefinition | Agent 元数据、发现规则和生命周期来源 |
| CapabilityReport | 当前版本实际支持的启动、取消、权限、输出和恢复能力 |
| TeamDefinition | 角色映射、候补、权限、预算、超时和强制关卡 |
| Run | 一次用户任务的目标、团队快照、任务图和当前状态 |
| TaskNode | 输入、角色、权限、状态、重试与完成证据 |
| Artifact | 代码、Patch、报告、数据文件、验证结果或复审结果 |
| Gate | 用户审批、确定性验证或独立复审关卡 |
| AuditEvent | Agent 调用、权限变化、用户干预、计划变更和强制放行 |

## 协作协议

采用三层协议：

1. 控制层：结构化提议，包含状态摘要、问题严重度、产物引用和建议动作。
2. 内容层：Markdown、代码、补丁、测试结果、报告和数据文件。
3. 日志层：原始输出、工具调用、错误与时间信息，独立保存并默认脱敏。

模型或适配器生成的控制信封一律是不可信提议。只有运行引擎可以依据既有策略和用户审批更新权限、预算、角色、任务图、关卡和完成状态。

## 安全不变量

- 不集中读取、复制、展示或保存 Agent 的 API Key、Token、Cookie 和账号凭证。
- 工作区文件、检索结果、网页、工具输出和其他 Agent 输出全部视为不可信数据。
- Agent 只能获得当前角色所需的最小上下文；每次调用记录上下文来源和范围。
- 写入、高风险、安装、新 Agent、团队外增援和权限扩大必须先展示预览并确认。
- 只读节点可以并行；首条闭环的写入节点始终单执行者串行。
- 达到预算、超时、重试或整改上限时暂停，模型不能自行追加额度。
- 强制复审放行必须由用户执行，并保存未解决问题和理由。
- 完成状态不确定的副作用节点禁止自动重试。

## 质量关卡

```text
规划关卡
  → 写入或高风险计划需要用户确认
执行
  → 每个写入节点只有一个执行者
确定性验证
  → 测试、构建、格式、来源、字段或 Dry Run
独立复审
  → 阻断 / 警告 / 建议
交付
  → 用户检查并选择应用、导出或放弃
```

阻断问题默认退回原执行者，最多整改两轮。复审者不直接修改被审产物。

## 失败与降级

固定的最低降级路径为：

1. 用户提供或确认计划。
2. 用户确认切换到一个健康执行 Agent。
3. 运行当前可用的确定性验证器。
4. 用户完成人工复审。
5. 交付物明确标记未达到原团队模板的独立复审等级。

不得静默跳过规划、验证或复审。所有 Agent 均不可用时终止任务，保留已有产物和审计记录。

## Workspace 与恢复

Git 项目使用隔离 Worktree，最终生成本地任务分支和提交；不自动应用到当前分支、不 Push、不创建 PR。

非 Git 首条闭环只生成插件任务目录内的独立产物，不自动修改现有目录。

只有具备可验证完成证据的节点允许自动恢复。写入节点至少记录：执行意图、目标、开始状态、产物指纹和完成证据。无法判断是否完成时暂停人工核对。

## UI 决策

首条闭环保留真实可用的可视界面，而不是后台原型：

- Agent 面板和团队配置。
- 会话侧边运行面板。
- 任务图、节点详情和人工干预。
- Agent 小人头像、角色徽章和轻量状态动效。
- 系统“减少动态效果”支持。

动效和自定义外观不构成核心正确性验收的阻塞条件，不建立独立复杂动画系统。

## 首条纵向闭环的当前默认范围

以下默认值用于继续推进，所有者可随时覆盖：

1. 四个外部 Agent 都进入面板检测；正式团队能力由兼容性验证结果决定。
2. 首条闭环先提供只读发现、版本、路径、冲突、鉴权和适配诊断；安装、升级、修复和精确卸载仍属于完整产品，但不阻塞首条核心闭环。
3. 同时验证一个 Git 任务和一个非 Git 独立产物任务，避免调度核心被写死为编程工具。
4. 非 Git 副作用写入与自动恢复不属于首条闭环。
5. 独立复审不可用时允许“确定性验证 + 人工复审”的明确降级交付。
6. 首条闭环默认不修改 Harness Core；若官方扩展面不足，先形成证据和变更影响，再由所有者决定 Core 补丁或 UI 降级。

## 进入编码的门槛

- Harness UI、事件、持久化和后台任务能力有第一方源码证据或最小复现。
- 首批 Agent 的 CapabilityReport 已完成，未知能力不能标为支持。
- 外部规划/复审价值评测的任务、指标和结果格式已冻结。
- 首条纵向闭环的 Provider 支持集合已根据证据确定。
- 安全不变量和失败降级路径已进入验收清单。
